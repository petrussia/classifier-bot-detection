# Детекция трафика автоматизированного сбора данных

## Результат и файл для сдачи

Готовый файл — **`submission.csv` в корне архива**. В нём 4 909 строк данных и ровно две колонки: `cookie_id,score`. Порядок соответствует `data/test.csv`. Score не округлялся до нескольких знаков и не преобразовывался в метки 0/1.

**Основная локальная оценка: Precision при Recall ≥ 70% = 0.807143** на отложенных датах 17–19 апреля 2026 года.

## Быстрый запуск

Для Python 3.14 устанавливайте зависимости из `requirements-py314.txt`:

```bash
python -m pip install --only-binary=:all: -r requirements-py314.txt
```

В этом наборе обновлены pandas и CatBoost для установки готовых пакетов на Python 3.14. После установки перезапустите ядро ноутбука. Исходный `requirements.txt` сохраняет версии эталонного запуска; побитное совпадение результатов с обновлёнными библиотеками не гарантируется.

Для исходного окружения Python 3.13:

```bash
python -m pip install -r requirements.txt
python solution.py --mode all
python tests.py
```

Команда `--mode all` заново читает CSV, вычисляет признаки, проверяет зафиксированный рецепт на отложенной выборке, обучает его на всех размеченных куки и записывает в файл **`artifacts/submission.csv`**.

Для повторного обучения без повторной валидации запусти:

```bash
python solution.py --mode train --output-dir reproduced
```

Для предсказаний уже обученными моделями из `artifacts/models` запусти:

```bash
python solution.py --mode predict
```

Для повторной проверки на отложенной выборке отдельно запусти:

```bash
python solution.py --mode validate --output-dir holdout_recheck
```

`solution.ipynb` содержит пояснения, фактические результаты, полный повторный запуск обучения и сравнение нового CSV с эталоном. Открывать ноутбук нужно рядом с `solution.py` и `data`. Jupyter не требуется для запуска Python-скрипта.

## Цель и метрика

Один объект — одна кука в заданном суточном окне. `target=1` означает трафик ботов, положительный класс, `target=0` — трафик, отнесённый к человеческому.

Применяется исходный скрипт `metric.py` из выданного архива, без изменений. Система выбирает максимум precision среди всех порогов, обеспечивающих recall не ниже 0.70. В submission передаются непрерывные оценки.

В отчётах `average_precision` — это `sklearn.metrics.average_precision_score`. Он, как и ROC-AUC используются для диагностики, не как финальная метрика итогового платформенного score-а.

## Данные и контроль утечек

Train содержит 11 091 куки и 899 положительных объектов; test — 4 909 куки. Исходный файл содержит 328 905 событий.

Очистка выполняется в таком порядке:

1. Присоединение единственного окна куки с проверкой `many_to_one`; проверка уникальности train/test-куки и непересечения наборов.
2. Фильтр **`window_start_ts <= event_ts < window_end_ts`**. Исключено 40 779 событий на правой границе или после неё; событий до левой границы нет.
3. Удаление полных дубликатов оставшихся строк: **4 293**. Остаётся **283 833** события. Разные события с одинаковой временной меткой я не удалял.
4. Сортировка по куке и времени, нормализация платформ и разбор User-Agent, построение признаков.

Во всём исходном файле было 4 863 дубля, но 570 из них уже исключены первым временным фильтром. Поэтому 4 863 и 40 779 нельзя складывать как непересекающиеся удаления. Все 16 000 куки имеют хотя бы одно событие в допустимом заданием окне.

Сырые `cookie_id`, `item_id`, полная строка User-Agent, абсолютные даты и события за пределами окна не входят в признаки. Идентификаторы объявлений используются только для подсчёта разнообразия и повторов. Возраст куки считается, как разность известных времён, а не как абсолютная дата.

Ни ручную, ни автоматическую псевдоразметку test-а я не применял. Признаки рассчитываются независимо для каждой куки: для предотвращения утечки данных совместная обработка train/test не переносит между ними статистики. Словари категорий и удаление констант при обучении определяются только по обучающим строкам.

Для одинаковых секунд задан технический порядок, а не предполагаемый причинный. Переходы между типами событий рассчитываются только для строго различных моментов времени. Пропуски координат остаются пропусками и не превращаются в неподвижный курсор в точке `(0, 0)`.

## Признаки и модель

Базовый блок `features.py` содержит 364 признака. В него входят частоты и доли действий, отношения контактов к просмотрам, разнообразие объявлений/категорий/городов/запросов, энтропия, статистики интервалов, сессии, часовая активность, регулярность, пагинация, покрытие координатами и движения курсора, возраст куки, нормализованная платформа и семейство браузера/ОС без версий.

`features_extra.py` добавляет 329 признаков: интервалы после удаления крупнейших пауз, отношения квантилей, форма распределения коротких интервалов, скользящие всплески активности, дополнительные переходы и навигация, листание внутри одного запроса, геометрия указателя. Нормировка координат 1920×1080 относится к диапазону этой выборки.

После удаления констант и дублирующего признака возраста CatBoost использует 355 признаков, LightGBM — 665. Числовые NaN обрабатываются деревьями нативно.

Итоговая формула определения моего score-а:

```text
score = 0.5 × mean(CatBoost(seed=42), CatBoost(seed=1337), CatBoost(seed=2026))
      + 0.5 × LightGBM(seed=42)
```

CatBoost: 1 600 деревьев, глубина 6, скорость обучения 0.035, L2=5, базовый набор признаков. LightGBM: 300 деревьев, 15 листьев, скорость обучения 0.03, минимальный лист 35, L2=5, доля признаков 0.85, расширенный набор.  
Функционал потерь, который я минимизировал в процессе обучения — логарифмическая функция потерь; выбор конфигурации - по требуемой precision-метрике. Все параметры находятся в `solution.py`, веса, seed-ы и история фиксации — в `final_config.json`.

Набор дополнительных признаков не оказался лучшим самостоятельным решением, но его ошибки полезны в ансамбле. Усреднение применяется к каждой куке отдельно, без ранжирования или калибровки по всему test.

## Валидация

Тест расположен после train по времени, поэтому случайное перемешанное разбиение не использовалось.

| Этап | Даты обучения | Даты проверки | Куки / боты на проверке | Базовая модель P@R≥0.70 | Ансамбль P@R≥0.70 |
|---|---|---|---:|---:|---:|
| Проверка A | 6–10 апреля | 11–13 апреля | 2 556 / 199 | 0.093220 | **0.838323** |
| Проверка B | 6–13 апреля | 14–16 апреля | 2 367 / 195 | 0.099639 | **0.816568** |
| Отложенная проверка | 6–16 апреля | 17–19 апреля | 1 951 / 160 | 0.095718 | **0.807143** |

Сравнивались LightGBM с разным числом листьев и весом положительного класса, CatBoost разных глубин, XGBoost, ExtraTrees, расширенные признаки, отбор 60/120 признаков, разные количества деревьев, семена и ансамбли. Рецепт выбран по среднему основной метрики на **двух** разбиениях для подбора моделей; среднее равно 0.827446.

Подбор достаточно широкий, поэтому валидационные оценки могут быть оптимистичны. Последние три дня train оставлены для отдельной проверки. Конфигурация основного решения зафиксирована до её выполнения и после её не менял.

На отложенной проверке при оптимальном диагностическом пороге отмечено 140 куки: **113 истинно положительных, 27 ложноположительных**. Т.е метрики Precision = 113/140 = 80.7143%, recall = 113/160 = 70.625%. AP = 0.800142, ROC-AUC = 0.941063. Этот порог не используется для бинаризации submission.

Одиночный расширенный LightGBM на отложенной выборке получил 0.829630, больше ансамбля. Однако на двух валидационных-разбиениях он дал только 0.769231 и 0.744565, заметно меньше ансамбля. Основной вариант не заменён на него после просмотра результатов отложенной проверки: это превратило бы независимую проверку в ещё одну выборку подбора. Все показатели компонентов сохранены в `artifacts/holdout_metrics.json`.

После проверки итоговые четыре модели переобучены на всех 11 091 размеченных куки; предсказания созданы для test 20–26 апреля.

## Проверки и воспроизводимость

`tests.py` содержит семь тестов: точные примеры метрики, сравнение с независимым перебором порогов на 200 случайных наборах с одинаковыми score, границы окна, полные дубли, неизменность признаков при изменении target/будущих событий, инвариантность значений признаков к переименованию куки с выравниванием колонок, корректный/некорректный submission.

В основном запуске проверены уникальность и порядок всех test-куки, конечность score, диапазон [0, 1], чтение CSV без потери точности, а также совпадение предсказаний до и после сохранения моделей. `solution.ipynb` дополнительно повторяет полное обучение с исходных CSV и сравнивает новый файл с эталоном.

## Содержимое архива

- `submission.csv` — готовые предсказания; `solution.ipynb` — пояснения и исполняемое воспроизведение.
- `solution.py`, `features.py`, `features_extra.py`, `metric.py`, `final_config.json`, `requirements.txt`, `tests.py` — основной код и настройки.
- `data/` — исходные данные train/test/events; `sample_submission.csv` — исходный пример формата.
- `artifacts/` — обученные модели, аудит, результаты проверок, предсказания валидации и хеши.
- `experiments/`, `crossval/` — фактические валидационные-результаты и прогнозы; `research/` — код повторения исследовательских экспериментов и оригинальный quickstart.

Полный повтор исследовательского поиска, который для получения submission **не требуется**:

```bash
python research/run_research.py
```

Он заново создаст `cache`, обучит исследовательские модели и пересчитает таблицы. Он не изменяет зафиксированный `final_config.json` автоматически и не использует отложенную выборку.
